# Agent 日程提案（#213）

`calendar_propose` 是现有助手和协作执行器共用的只读工具。它校验标题、含时区的整分钟起止时间、当前未归档事项 ID，返回 `calendar_proposal` v1。来源使用实际任务/执行编号，提案及首次保存编号由来源和规范化内容稳定生成；没有任务上下文时拒绝执行。不按标题猜事项，也不解析模型自由正文来执行。

提案保存在原任务事件中，协作历史只投影该事件；不建立第二份持久草稿库。聊天、桌宠聊天和执行详情提供“打开日程草稿”。桌面工作台通过原认证 RPC `read_calendar_proposal(task_id, proposal_id)` 重新读取任务事件、当前事项和原保存回执，交给与事项拖入共用的 `createCalendarDraft` 和 `CalendarEventEditor`。浏览器远程协作范围不能调用这条桌面能力。

协作执行器只在选中“日程提案”能力时提供该工具，tebb身份不能绕过开关；内置tebb的默认工具列表包含该能力。

打开不会创建日程或事项关联。取消丢弃本次编辑，原提案可以再开；再次明确打开同一提案必须重新显示表单。只有用户点击保存才经 `LocalCalendarController.change` 调用原 `change_local_calendar`，首次创建使用提案固定的本地编号及 `save_request_id`。默认不勾选飞书同步；用户仍可调整字段或明确同步。完成日程安排不推进事项业务状态。

读取结果含明确状态：

| state | 含义与界面动作 |
| --- | --- |
| proposed | 原提案有效，可打开共用草稿表单 |
| saved | 原保存回执确认且日程仍在，定位已保存安排 |
| consumed | 原保存已确认、日程已移除，不重新创建 |
| unconfirmed | 状态/原回执缺失或未知，只读取原编号核对 |
| blocked | 原任务/协议/当前来源事项无法核实，不打开新草稿 |

即使已有同编号日程，原保存回执未知或缺失也不宣称保存已确认。前端保留原待核对标记；读请求和重开不重放写操作。移除已保存安排后重新安排，需要一次新的明确意图及提案，不能复活已消费提案。

Agent 原先直接创建日程的旁路已移除，`calendar_change.create` 拒绝并提示使用提案。人工看板创建和已确认日程的现有编辑/同步入口保留。

## 调试与验收

复用原任务、模型调用记录、工具回执、`calendar_proposal` 事件及原本地日程/事项读取接口，不启动另一套 Agent。调试时必须使用隔离数据及外部适配器，不能以模型说“已创建草稿”代替界面验收。

统一入口：`python scripts/eval_agent.py --case calendar_proposal --limit 1 --samples 1 --output <新的隔离目录>`。默认合成模型；显式 `--live` 使用已授权模型。真实评测只复制所需模型配置到隔离目录，只发送合成事项与时段，不读取真实任务/聊天；凭据结束删除。确认前按实际服务核对日程、事项关联及来源事项均未改变。评测报告明确标注 `ui_confirmation=not_exercised_by_model_case`，模型部分不能代替表单操作。

本批一个真实模型样本：3 次调用、1 次 `calendar_propose`，输入/输出 6108/1795 tokens，约44.8秒，费用未知；实际工具事件和零写入核对通过。随后同一份原提案使用实际产品卡片、导航、周历及编辑表单，连接隔离的真实认证 API：取消和重开后0日程/0关联；点击保存后1日程/1正确事项关联；再次打开定位原安排且数量仍为1。620px窗口核对字段、来源事项和未勾选同步。外部飞书适配器禁写，未操作真实飞书。

协议篡改、自由正文、不同任务、来源归档、已消费、未知/缺失回执、能力禁用及丢响应恢复有确定性回归。原始集成失败、测试加载失败及重开缺陷分别保留；本机全量1168项的旧评测目录数量断言失败也保留，随后更新34案清单并补充实际工具/独立验真缺一不可的反例。不覆盖旧结果。最终精确提交与完整 CI 以 [#213](https://github.com/liukun158959-beep/tebb/issues/213) 记录为准；本例不证明通用模型质量或性能门槛已通过。
